# VPN на Photonicat 2

Установлены **два ядра и два активных выхода**: один выбранный профиль AmneziaWG
и один выбранный узел Mihomo. Остальные профили и узлы — сохранённые варианты,
отдельных туннелей для них нет. Подписки обновляются раз в сутки; фоновые проверки
всех узлов отключены, поскольку часть серверов предназначена для мобильных сетей.

Текущие версии:

- Mihomo v1.19.32, официальный Linux ARM64, SHA256 архива сверена с GitHub asset digest.
- Официальный amneziawg-go, тег v3.1.20260828, commit
  `b5928efb6ca19f0153958460c3d141f04abc5c2e`, сборка Go 1.27.1,
  `CGO_ENABLED=0 GOOS=linux GOARCH=arm64`, trimpath, без debug symbols.
  Встроенная строка версии в этом исходнике устарела; версию определяет тег/commit.

Оба проекта используют Go. Для этой установки выбрана совместимость официального
AmneziaWG с предоставленными конфигами 2.0 и 3.1. Это не утверждение о максимальной
скорости: сравнительный тест Go/Rust/kernel здесь не проводился. У Rust-форка
WireSock BoringTun заявлены расширения AmneziaWG, но полная совместимость именно с
предоставленными параметрами 3.1 в этой работе не установлена. Сторонний модуль
ядра Linux не устанавливался, существующее ядро прошивки сохранено.

## Где находится служба

### Локальная настройка WAN от 2026-10-21

По запросу владельца WAN (`eth0`) разрешает только 1000BASE-T Full Duplex.
Это отдельная настройка данного роутера, не общий стандарт установки для форума.
UCI: `network.pcat_wan_link` — device, name=eth0, speed=1000, duplex=1,
autoneg=1. Автосогласование сохранено, но режимы 10/100 не объявляются.
LAN и автоматический выбор роли WAN не менялись.

`wan-link.sh` повторяет настройку после появления PHY: init
`photonicat-wan-link` (START=99) и iface-hook `95-photonicat-wan-link` для
wan/wan6/pcwan. Это обход неприменения UCI-настройки штатным netifd.
Оба читают скорость из UCI, поэтому ручная смена на 100 сохраняется:

```sh
uci set network.pcat_wan_link.speed=100
uci commit network
/etc/init.d/photonicat-wan-link reload
```

Для возврата Auto удалить секцию `network.pcat_wan_link`, сохранить network,
затем выполнить `ethtool -s eth0 autoneg on advertise 0x2f`; hooks без секции
ничего не меняют. Резервная копия до изменения:
`/root/pcat-backups/network.before-wan-gigabit-20261021`.
Проверены фактическое объявление только 1000baseT/Full, запуск init и iface-hook,
LAN 1000 и интернет LAN через Mihomo. WAN при проверке без кабеля;
физическое соединение WAN и полная перезагрузка пока не проверялись.

- `/opt/photonicat-vpn/`: два бинарника и `manager.py`.
- `/etc/photonicat-vpn/`: секреты, четыре исходных AWG-конфига, подписки,
  конфигурация Mihomo, список профилей и выбранные значения.
- `/etc/init.d/photonicat-vpn`: procd, по одному экземпляру каждого ядра,
  отдельный процесс восстановления маршрутов и выбора.
- `/var/run/photonicat-vpn-awg.json`: реально применённый AWG-профиль и PID.

Автозапуск включён. Перезапуск именно VPN-службы с сохранением выбора проверен;
перезагрузка всего роутера не выполнялась. Файлы добавлены в sysupgrade.conf.
До установки сохранена отдельная резервная копия конфигурации. Секретные каталоги
доступны только root; исходные профили и ссылки подписок не включены в исходники
приложения. Конфиги подписок используются как провайдеры узлов: их собственные
глобальные правила, DNS, слушатели и скрипты не применяются.

## Управление и будущая интеграция с приложением

Команды выполняются локально от root, вывод — JSON без ключей и URL подписок:

```sh
python3 /opt/photonicat-vpn/manager.py status
python3 /opt/photonicat-vpn/manager.py select-awg demo-profile
python3 /opt/photonicat-vpn/manager.py select-node 'Demo server'
python3 /opt/photonicat-vpn/manager.py select-engine amneziawg
python3 /opt/photonicat-vpn/manager.py select-engine mihomo
```

`status` разделяет выбранный и реально применённый профиль, возвращает доступные
варианты, состояние интерфейсов и счётчики/handshake AmneziaWG. `running` означает
работающий интерфейс/процесс, а не доказанную доступность интернета через сервер.
Выбор узла допускается только из списка Mihomo; выбор AWG — только из manifest.
Загрузка arbitrary shell hooks из AWG-конфига запрещена.

Смена AWG-профиля пересоздаёт только один экземпляр amneziawg-go, чтобы параметры
3.1 не оставались после перехода на 2.0. Mihomo продолжает работать. Смена узла
Mihomo не трогает AWG. Переключение активного ядра не перезапускает ядра.
Выбор сохраняется и восстанавливается после перезапуска службы. При отказе
контроллера Mihomo нативный маршрут Amnezia остаётся доступен для выбора.

В приложении 0.3 есть отдельная вкладка VPN: профиль Amnezia, сервер Mihomo
и активный выход выбираются независимо через защищённую BLE-службу. Проверка
интернета выполняется самим роутером через выбранное ядро и показывает внешний IP.

## Импорт и управление каталогом

Amnezia: файл `.conf`, JSON с готовым AWG-конфигом или QR с готовым конфигом
(включая `vpn://` с Qt-compressed JSON). Ключи доступа, требующие получения
конфигурации через API Amnezia, пока не поддерживаются: нужен экспорт `.conf`.
Подписки Mihomo: HTTPS-ссылка на Clash/Mihomo YAML или QR с такой ссылкой.
Сканер поддерживает камеру и изображение из телефона. Исходные ключи и ссылки
не входят в ответ каталога; импорт передаётся по зашифрованному BLE-каналу.

Ограничения: 24 профиля AWG, файл до 24 КиБ, 8 подписок и до 64 серверов суммарно
при добавлении. Список, выросший при автоматическом обновлении, показывается
частично с предупреждением. YAML-алиасы и команды PostUp/PostDown не принимаются.
Добавление не активирует профиль. Выбранный AWG-профиль, подписку выбранного
сервера и последнюю подписку нельзя удалить без предварительной смены выбора
или добавления замены. Новая конфигурация Mihomo проверяется перед применением;
при неудаче восстанавливается предыдущая.

`router/vpn_control.py` принимает только фиксированный набор действий и проверяет
ревизию каталога перед изменением. Каталог обслуживает `catalog.py` рядом с manager.py.
Новых сетевых портов управления не открывается.

## Маршруты и порты

| Выход | Интерфейс | Таблица / метка | Локальный HTTP/SOCKS порт |
|---|---|---:|---:|
| Выбранная Amnezia | pcawg0 | 23501 | 17881 |
| Выбранный Mihomo | pcmh0 | 23502 | 17882 |
| Выбранное активное ядро | один из двух выше | 23500 | 17880 |

Все прокси-порты слушают **только 127.0.0.1**. Контроллер Mihomo —
127.0.0.1:19090 с отдельным секретом; DNS Mihomo — 127.0.0.1:10553.
Локальные HTTP/SOCKS-входы обслуживает Mihomo, включая тестовый вход к AWG.
Нативный AWG-маршрут через pcawg0 независим от процесса Mihomo. При остановке
Mihomo его локальные прокси-порты, естественно, недоступны.

Пакеты с метками направляются в отдельные таблицы IPv4/IPv6. В каждой таблице
есть `unreachable default` с большим metric, чтобы исчезновение интерфейса не
отправляло помеченный трафик через обычный WAN. Внешние UDP-пакеты AWG получают
отдельную метку 23499 и выходят через обычную основную таблицу, без петли.

По умолчанию физический LAN (`br-lan`) получает метку активного ядра. Независимая
таблица `inet pcat_ports` разрешает выход только в выбранный VPN-интерфейс; нет
исключения для established-соединений. Выключатель LAN опустошает набор разрешённых
выходов. После остановки всей VPN-службы защита остаётся. В fw4 также установлен
резервный запрет прямой пересылки LAN. Flow offloading выключен, чтобы ускоренные
потоки не обходили проверки. Это может повлиять на максимальную скорость;
сравнительный тест пропускной способности не выполнен.

DNS TCP/UDP 53 от LAN, включая запросы к самому роутеру и произвольным DNS-адресам,
перенаправляется на Cloudflare внутри выбранного VPN для IPv4 и IPv6. DoH/DoT
клиентов подчиняется той же политике маршрутизации. Mihomo использует
`https://1.1.1.1/dns-query#PC-Mihomo` для клиентских имён; разрешение имён самих
VPN-серверов — отдельный прямой DoH bootstrap. Пустой провайдер имеет запасной
`REJECT`, а не прямой выход. TUN использует gVisor: TCP работает без разрешения
входящих соединений в защищённой VPN-зоне. IPv6 LAN маскируется в VPN; при отсутствии
рабочего IPv6-туннеля прямого обхода нет.

Direct Wi-Fi использует `br-pcdirect`, адрес 172.16.16.1/24. Защищённый Wi-Fi
использует `br-pcwifi`, адрес 172.16.48.1/24 и отдельную ULA /64. Каждая
поддерживаемая AP-плата назначается независимо; номера radio в приложении не зашиты. WAN в режиме
раздачи получает 172.16.32.1/24, также прямой выход через имеющийся uplink.
Режимы WAN: авто, приём, раздача. При обнаружении внешнего DHCP или IPv6 Router
Advertisement выбирается приём, даже если запрошена раздача. Отсутствие интернета
у внешнего роутера само по себе не переводит порт в раздачу. Для сети со статической
адресацией нужно выбрать приём и отдельно настроить адресацию. Обычное определение
роли после подключения занимает примерно 20–25 секунд.

`photonicat-ports` запускается до сети; на старте возвращает WAN в безопасную роль
приёма. При смене роли ожидает готовность интерфейса, переключает физический запрет
DHCP и принадлежность `wan`/`wan6` к внешней зоне, затем обновляет fw4 и dnsmasq.
Одного отключения логического интерфейса недостаточно: прошивка может сохранять
его физический порт в прежней зоне. Раздача не считается готовой до этих операций.
Конфигурация — `/etc/photonicat-vpn/ports.json`, состояние —
`/var/run/photonicat-ports.json`. Проверка холодного старта всего устройства ещё
не проводилась; проверялись перезапуски служб и firewall.

Hot swap применяется к новым соединениям/пакетам по выбранной политике.
Бесшовное перенесение существующего TCP-сеанса между разными внешними IP
не обещается; соединение может потребовать переподключения. Автоматическое
переключение по недоступности сервера пока не включено.

## Проверка и откат

Локальные проверки: `python3 -m unittest discover -s vpn-service -p 'test_*.py'`.
Фактические результаты работы на роутере: `output/qa/vpn-verification.json`.
Проверены четыре AWG-профиля последовательно, IPv4/IPv6, четыре узла первой
подписки, маршруты обоих ядер, UDP DNS, передача данных, смена выхода,
закрытый маршрут при отключении AWG, переход на AWG при зависшем Mihomo,
восстановление выбора после перезапуска VPN-службы.

15 узлов мобильной подписки импортированы; при первоначальной проверке
в стационарной сети запросы не прошли. Все эти узлы на модеме пока не перебирались.
На мобильном uplink 20 октября проверен текущий Mihomo RW USA via DE XHTTP:
IPv4, IPv6 и DNS работают. Текущий AWG PC-USDE-31 в этой мобильной проверке
не получил handshake; трафик LAN при его выборе блокировался. На домашнем
uplink тот же AWG ранее проходил проверки. Причина различия ещё не установлена.

При остановке VPN LAN намеренно остаётся без интернета:

```sh
/etc/init.d/photonicat-vpn stop
```

WAN и подключения в режиме Direct продолжают работать. Wi-Fi и LAN в режиме VPN
остаются заблокированы. Остановка `photonicat-ports`
сохраняет защитные правила. Это не команда отката сетевой миграции.
До миграции сохранены network/firewall/dhcp/wireless и конфигурации служб в
`/etc/photonicat-vpn/backups/ports-v04/`; закрытая копия на Mac — `.private/ports/`.
Полный откат требует согласованного восстановления сети, DHCP, firewall и служб
с локальным доступом, а не одиночного удаления правил. Старую копию нельзя
восстанавливать поверх более поздних пользовательских настроек без сравнения.
Установщик для публичного выпуска ещё не подготовлен.

Результаты проверки LAN и отказов обоих ядер: `output/qa/ports-v04-live.json`.
Изолированная проверка выдачи адреса и прямого мобильного выхода:
`output/qa/ports-v04-share-isolated.json`. Физический WAN проверен на Mac после
исправления принадлежности порта к зоне: адрес 172.16.32.132, внешний мобильный
IPv4 203.0.113.10. Неуспешные первые попытки не считаются пройденными тестами.

Дополнительная проверка Mihomo 20 октября: `output/qa/mihomo-leak-audit.json`.
Тестовый клиент входит через тот же `br-lan`: DNS TCP/UDP к адресу роутера и
жёстко заданным сторонним адресам, HTTPS и DoH по IPv4/IPv6. Проверены работа,
SIGSTOP ядра и восстановление. Метки DNS, HTTP и пробных UDP-пакетов видны
на LAN/TUN и не обнаружены на внешних интерфейсах. При SIGSTOP DNS, DoH и HTTPS
не проходят. Это проверка маршрутизации LAN, а не гарантия отсутствия любых
браузерных способов идентификации; результат относится к проверенным клиентам и сценариям.


## Режимы подключений и СМС — 0.5

После базовой установки портов `install_wifi_vpn.py` создаёт пустой защищённый
bridge и правила до назначения AP. `install_lan_modes.py` добавляет возможность
явного выбора Direct для LAN; исходный режим остаётся VPN. LAN сохраняет свою
подсеть и адрес управления при переключении. Конфигурация — `ports.json`:
`lan_mode` (`vpn`/`direct`), `wifi_bridge`, `wifi_address`, флаги готовности.
Режим AP хранится в UCI wireless.network (`pcdirect`/`pcwifi`).

У LAN и защищённого Wi-Fi независимые наборы разрешённых выходов. Пауза LAN
не отключает Wi-Fi. Для Direct LAN используется метка основного маршрута и
отдельное разрешение в резервной защите fw4. В режиме VPN возвратные пакеты
LAN с других интерфейсов также блокируются. Все изменения структуры таблицы
nft применяются одной транзакцией; пустой набор выходов не содержит `elements`.

СМС читаются через штатный `/api/v2/sms/list.json`, фильтруется направление incoming.
BLE-команды `sms_list` и `sms_read` не отправляют и не удаляют сообщения. Детали
только по запросу, до 6000 символов; превью до 140, 10 записей на страницу.
Вентилятор использует штатные `/api/v1/fan_mode.json`, `fan_speed.json`,
`fan_speed_actual.json`; команды не пишут sysfs и не заменяют температурный алгоритм.

Результаты: `output/qa/wifi-vpn-leak-audit.json`,
`wifi-vpn-service-stop-audit.json`, `lan-direct-vpn-audit.json`,
`lan-v05-leak-recheck.json`, `sms-v05-live.json`. В проверке защищённого Wi-Fi
успешны DNS TCP/UDP IPv4/IPv6, HTTPS и DoH, перезагрузка firewall и независимость
от паузы LAN. При SIGSTOP Mihomo и полной остановке VPN-службы запросы не проходят,
открытые тестовые маркеры не обнаружены на внешних интерфейсах.

Запись настроек вентилятора получает обычный CSRF-токен с cookie сеанса штатной
локальной службы. Защита CSRF не отключается, административный пароль в приложении
или службе не сохраняется. Подтверждение записи — повторное чтение штатного API.
Резервная настройка вентилятора — `/etc/photonicat-companion/backups/fan.before.json`.
